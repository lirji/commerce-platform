# 运营体验审计摘要

平台已经具备商品与库存、会员、营销、交易和运行处置的主要操作。当前阻碍集中在运营判断所需的事实分散：同一对象的门店、状态、原版本、金额或结果往往要到第二个页面确认。优先修复会误导范围和查询的问题，再做交易下钻与高影响动作的前后对照。

本次逐页审计覆盖 **73 个角色×业务页面入口**。本机同版本演示环境实测旧管理员 29 页和会员 7 页，另复查 9 个窄屏页面及 5 条只读路径。中央 36 条业务路由查到页面壳，环境未开启中央身份，组织入口直接访问返回 401。中央内部页面内容、字段和流程来自源码，真实岗位操作待复验。 [系统覆盖及证据](01-system-overview.md)。

## 十个优先问题与对应改造

| 顺序 | 优先问题 | 优先改造及产出 |
| --- | --- | --- |
| 1 | 订单页展示选店，但旧订单列表请求不随壳层门店限定。本机已观察到请求差异。 | 明确订单列表实际范围。完成真实的结构化店铺筛选后，用两店数据验收查询与上下文一致。 |
| 2 | 中央组织默认入口 `/operations` 同源 GET 401。 | 补精确入口映射及登录壳，保护全部业务 API 并验证授权后的默认落地页。 |
| 3 | 中央运营页面显示关键词、状态和每页，但目录请求忽略条件且固定50条。 | 复用现有 Owner 查询契约，接入真实条件和页大小，逐条件验收。 |
| 4 | SKU 首屏有两个作用对象不同的搜索。实测上方搜索未改变 SKU，下方同样词才筛为零。 | 把筛选归到 SKU 和 SPU 各自页签，统一术语、清理旧批量选择。 |
| 5 | 支付、履约、售后、退款要手工串号，未知与完成容易混读。 | 完整详情增加分区和精确授权下钻。支持支付读取、申请/退款关联及返回查询。 |
| 6 | 收货、调价和批量计划的原对象、前后值与执行窗口难同屏核对。 | 执行前展示店、SKU、旧值、新值及数量，执行后给真实行级结果，保留并发检查。 |
| 7 | 活动、人群与预算各有固定版本及状态，但发布人需跨页核对。 | 同一活动版本接授权预算和资格摘要，明确预览、待审批、生效和真实资金占用。 |
| 8 | 发券停发、撤回与逐人结果各有操作和状态，当前结果解释分散。 | 发券预检显示固定券、快照与额度，批次回执区分已发、撤回、保留、未处理和失败原因。 |
| 9 | 中央商家与门店两区共用筛选状态键，业务对象不同时会沿用同一查询条件。 | 按商家与门店拆分状态键，验收切换、刷新、返回均恢复各自查询。 |
| 10 | 窄屏订单中常用和低频条件一起占据首屏，核心任务需要滚动才能开始。 | 关键词与状态常驻，日期高级折叠，保留范围、筛选摘要和返回焦点。 |

## 主要运营风险与预期价值

真实资金状态判断、批量改价/库存、活动额度、发券撤回、跨门店授权与重放值得最先验证。源码中已有范围检查、固定版本、审计、原意图和未知资金保护。本次审计未观察到资损或越权，正式渠道和岗位组合证据仍待补。前两阶段目标是降低因错误条件和不明确范围产生的误判，缩短单笔交易和营销问题的查阅路径，降低操作前重复核对的负担。5 步订单查看路径在支付只读摘要接好后预计少 1 步。SKU 的误用路径可少两次操作，已经使用正确筛选的用户步骤相同。所有收益保留为任务级指标，等待岗位数据复验。

推荐顺序为 **入口、筛选和风险验证 → 核心目录与详情 → 跨模块定位和实际回执 → 待办、导出等长期能力**。尚未验证中央真实 SSO 和权限组合、平台身份、两店数据下的误操作、真实渠道、业务写入、规模化 SQL 性能与全量无障碍。业务需要确认风险阈值、审批岗位、正式渠道与敏感导出范围。 [流程](04-business-workflow-optimization.md)、[风险](05-operation-risk-audit.md)、[改造清单](07-optimization-backlog.md)、[路线图](08-implementation-roadmap.md)。
