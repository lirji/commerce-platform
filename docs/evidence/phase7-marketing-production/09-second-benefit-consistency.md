# 券一致性与事务边界

订单创建事务：积分预留→已有钱包券占用→活动赠券定义行锁及额度预留→活动预算→CREDIT（如配置）→库存→营销执行。任一步失败，命令、额度、预留和执行一起回滚。支付确认事务：钱包券确认→活动赠券发放→预算→CREDIT 请求→库存→执行状态。券发放失败使整个订单支付状态迁移回滚；可信支付事实保持在事件表，由原事件重试/隔离恢复，不能错误标记营销已授予。

MySQL 定向测试：配额 1 时首单预留后 `reserved=1, issued=0`，第二单 409；支付后 `reserved=0, issued=1`，`marketing_execution=GRANTED`、钱包来源 CAMPAIGN 仅 1 行、券 ID 与执行引用相同。取消后额度归零、无钱包券，下一单可预留。最后一份额度双请求测试也在新增用例中。

券定义行锁与 `issued+reserved<quota` 条件更新保护所有受控发行来源；CHECK 再承担最终约束。`source_type/source_id` 唯一键与订单预留主键防重启和多实例重复发放。实际双实例事件竞争与故障注入均已通过，详见 `12-multi-instance.md`、`13-failure-injection.md`。最终独立进程压测还证明 120 用户/30 额度的两节点批量业务结果。
