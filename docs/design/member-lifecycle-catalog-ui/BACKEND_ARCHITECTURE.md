# 模块与一致性

member 独占资料、成长、周期和积分账本；benefit 独占券和权益。trade 保留报价快照；order-runtime 在订单事务调用积分公开 API 进行冻结/消费/释放。aftersales 提供权威退货行，积分返还依据原分配而非现金退款反推。
commerce-app 负责跨模块事件装配，不能使 member 反向依赖 benefit/order。marketing-automation 持有触达/旅程/效果投影，catalog 持有商品经营与任务；UI 只能读取公开 API。

## 周期模型（LP01）

周期锚点为不可变策略 effectiveFrom，UTC 固定 periodDays。升级依据本周期净成长；保级依据上一周期净成长；等级为两者可达等级的较高者，每次边界后上一周期资格替换更早周期。退款修正原订单所在周期，防止退历史订单污染当前周期；周期配置发布前的订单不追溯赠成长。人工调整按调整时间归属。每次权威变更在会员行锁内对账，且定时器推进到期边界。跳过多个周期直接计算当前和上一周期，不无限补发历史权益。

周期账户记录当前边界/等级/版本，只有周期评估负责写等级；原累计成长仍保留用于分析。每会员/周期/等级权益来源唯一，跨域发放走可靠事件和同源幂等。退款降级不会假称收回已经消费权益，需要明确权益余额/债务展示。

## 风险与兼容

V1–V22 已执行，后续只增加迁移。旧 JSON 新字段须有空值默认和旧构造兼容；报价到期窗口内旧单照常处理。所有经济策略版本不可变且记录生效时间，报价冻结最终仍重验可用余额。锁顺序统一会员→积分→券/权益→商品；实际接入订单时校验现有顺序避免反转。
异步失败保留失败状态/来源标识，可重试，不能显示成功。扫描最多 100，任务每轮有界并以数据库提交为检查点；不使用全库长事务。机密不入日志、Git 或页面。

## LP02 影响确认

benefit 增加等级礼包所有权，直接依赖已存在 member 公共 API；消费 member.cycle.assessed.v1，无新增循环。礼券尚未混入等级权益包（等级券可经旅程/定向券处理）。member 公共策略单版本查询服务于绑定校验。V24 仅扩展权益来源约束并新增礼包表。礼包发放在会员行锁后获取权益定义配额，沿用本地事务和 Outbox，避免外部调用延长锁。

## LP03 积分数据与影响 Gate

积分与成长分账：member_point_policy/account/order/refund/lot/ledger均属于member，Mapper XML集中SQL。批次保留原奖励、剩余、冻结、已过期数量及原有效期，退款先抵扣已过期免扣部分，避免过期后退款产生虚假负担。账户存待偿扣回及版本，可用余额从未过期批次扣除待偿值得出；不得只读可能滞后的到期投影。会员行锁串行化来源、调整、退款和过期，账本/Outbox同事务。
commerce-app新增事件适配复用权威订单/退款查询，member不依赖order/payment。V25新增积分表，不修改已应用迁移。已有API与订单金额不变（抵扣归LP04），本片不引入新依赖。验证必须包含退款先到、重复/并发、策略切换、过期读取、过期退款免扣、人工扣回债务与后续获取抵偿、角色/租户隔离。三Gate据此PASS，可实施LP03。

LP03索引审查：V25已执行后追加V26 active_balance生成列及会员/到期索引，钱包和任务只查有余额批次，避免账本增长后反复扫描全部耗尽历史。原历史索引保留兼容。

## LP04 影响与一致性 Gate

member新增PointsSpendApi及本域持有/分配/返还来源表，trade只调用公开预览，order-runtime调用预留/终态，aftersales调用返还。订单先锁自己订单、再锁会员，再触及券/预算/库存；积分服务不反向锁订单。取消、回调及到期所有分支均以相同顺序处理。积分批次到期仍保留冻结，终态释放时处理原有效期。账户与批次更新共享本域积分写入助手，不复制经济规则。

V27增加持有/分配/返还及held账本快照；V28增加售后行积分列。全为扩展；旧订单无积分时消费端口应幂等空操作。测试必须覆盖并发下单额度争抢、报价后改规则/失效/余额变化回滚、支付UNKNOWN不释放、明确取消、零现金支付及退货、分次退款守恒、已过期释放和原奖励退款后返还抵偿。效果平台成本沿用Quote.funding，独立积分成本比较归LP08继续展开。三Gate PASS，可实施LP04。

LP04发布/回退边界：仅承诺新应用可读取旧报价/订单；积分启用后不允许回退至不处理积分持有的旧应用。先扩展数据库、更新全部交易写入实例，再由运营开启spendEnabled；不允许混用新旧交易写入实例处理积分单。当前部署为单应用进程，无滚动发布承诺。出现问题先关闭新积分消费、保留新代码完成在途单，再做补偿/前向修复。新请求redeemPoints为空时不序列化入幂等摘要，保留旧报价命令重放兼容。

LP04必要附带修复：三次部分退款21.66+21.66+21.67触发旧PaymentMapper.reserveRefund金额比较冲突。真实MySQL证明 DECIMAL(43.32)+'21.67' <= DECIMAL(64.99)为false、显式DECIMAL参数为true；仅修正该退款额度SQL的参数运算类型，不能放宽资金上限。由PointsCheckoutTest部分退款守恒场景保护。

## LP05 兑换边界

benefit.PointOffer编排会员积分扣费和受控来源券/权益，同一Commands事务。member_point_exchange只记录积分消费来源，不拥有券定义；benefit_point_redemption记录真实资产ID。每人计数和总额度有锁、唯一键与CHECK兜底；会员行→目录行→资产定义固定锁序。兑换内容不可变，停启CAS审计。SOURCE_ONLY禁止公共领取。权益REQUESTED仍由原Outbox/Inbox消费者推进，回执不冒充到账。
