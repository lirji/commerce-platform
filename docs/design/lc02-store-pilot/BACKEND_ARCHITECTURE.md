# LC-02 首店范围改造方案

实施从 `commerce-platform` 的 `merchant`、`store`、`catalog` 开始，复用现有门店目录、商品目录与营销工作台。选品、预算、隔离范围和交易报价时序见[首店满减试点实施方案](PILOT_OPERATIONS.md)。正式支付、退款分摊和关账沿用 [LC-02 至 LC-06 总计划](../../../../marketing-lowcode-platform/docs/design/lowcode-commercialization/IMPLEMENTATION_SLICES.md)。

## 1. 业务目标

运营能用权威目录核定一个真实商户、一个授权组织、一个参与门店、同组织一个对照门店和参与门店的一款已发布 SKU。营销沿用人民币固定满减和单一出资账户。对照门店用于验证排除规则，营销活动和机器绑定授权只覆盖参与门店。

验收时，审核人可以从范围版本追溯门店、商品和订单归属。参与门店的合规订单可以进入既有营销流程。对照门店、错租户、错商品和来源待查的订单均留在试点范围之外。已承诺的订单继续按原报价和账本处理。

## 2. 现有事实与责任边界

| 证据 | 权威项目与实现 | 对本次设计的影响 |
| --- | --- | --- |
| F1 商家、门店和目录 | Commerce 的 `StoreApi.View` 保存 `storeId`、`merchantId`、状态和版本。`StoreService` 校验租户及启用商家，`CatalogService` 按租户、门店、SKU 和渠道读取可售目录。已有 `GET /v1/admin/merchants`、`GET /v1/admin/stores`、`GET /v1/catalog?storeId=…` | 用现有读取能力收集范围证据，保留目录的员工授权校验 |
| F2 商城订单 | Commerce 的 `order-runtime` 从已校验的报价写入商城订单的商户、门店和报价引用 | 商城订单可以提供门店来源，需另有受信关系连接到同一笔原生交易 |
| F3 原生交易 | `transaction-center` 下单持久化交易租户、商户和原生订单标识。本次查看的订单写入和营销交易回执均缺少独立的商城门店归属字段 | 交易租户和商户限定所属商户范围。逐单门店来源另行核验，仓库编号和商品编号只作各自领域的凭证 |
| F4 营销活动与绑定 | 营销 Control 的满减模板要求一个活动归属门店、一款 SKU 和 CNY。资金绑定核对原始签名报价的订单号，并以已授权机器的营销租户、交易租户、组织及门店限定申请范围 | 复用既有活动和机器入口。签名者必须从已核验的来源构造门店与商品声明 |
| F5 组织和授权 | `auth-platform` 维护中央身份和授权，Commerce 提供门店事实。营销资金按 Casdoor 客户端和主体配置有限范围 | 由 Auth 与各系统责任方签收组织、租户和机器配对。Commerce 的商户编号与营销组织编号各自保留 |

源码入口见 [商城管理接口](../../../commerce-app/src/main/java/com/lrj/commerce/app/http/commerce/CommerceController.java)、[门店服务](../../../store/src/main/java/com/lrj/commerce/store/management/application/StoreService.java)、[商品服务](../../../catalog/src/main/java/com/lrj/commerce/catalog/assortment/application/CatalogService.java)、[交易下单](../../../../transaction-center/transaction-order/src/main/java/com/lrj/trade/order/OrderService.java)和[资金绑定运行手册](../../../../marketing-lowcode-platform/docs/operations/RUNBOOK.md#交易订单绑定)。

## 3. 改造决策

**D1 用已有目录与受控配置交付单店试点。** 在获授权环境查询真实商户、参与和对照门店、指定 SKU。运营、Commerce、Auth、交易和营销资金共同确认一版范围记录。记录按环境和版本保管，私密部署配置仅引用该版本。首期适用于一个参与门店，变更门店或 SKU 走新版本复核。

| 范围记录 | 签收字段 | 核验责任 |
| --- | --- | --- |
| 商城来源 | 环境、商城租户、商家 ID、参与和对照门店 ID、门店状态及版本、指定 SKU 和商品修订，附来源时间 | Commerce、商户运营 |
| 交易范围 | 原生交易租户、商户标识、对应商品标识、可关联商城门店的订单来源及证据引用 | 交易中心、Commerce |
| 营销范围 | 营销租户、组织、参与与对照 `shopId`、参与 SKU、活动版本、CNY 出资账户 | 商户运营、营销产品、资金 |
| 授权与变更 | 机器客户端引用、签收角色、范围版本、生效窗口、环境、变更及停止责任人 | Auth、营销资金、运维 |

同名显示值只供人工查看。所有映射按原标识和租户组合精确匹配。若不同系统为同一个门店或商品采用不同编号，由双方确认显式映射。签收记录保留来源引用、当前版本和变更历史。仓库证据只存脱敏引用，凭据留在现有密钥渠道。

**D2 签名前核验报价来源，绑定前核验订单关联。** 优先复用能证明原生订单和商城门店的可信持久记录。对已确认存在缺口的隔离试点，由交易中心持有带版本的交易报价引用，在签名前核验商城服务提供的租户、商户、门店、商品和有效范围版本。下单落库时冻结关联，使用 `(原生交易租户, 原生订单 ID)` 及单报价单订单约束。同一关系重试返回原结果，改挂其他门店产生冲突。无法验证、证据缺失或存在歧义时，试点路径保留待核查。

条件改造需先签收写入责任、受信调用方、下单时序和接口契约。关联与该关系所属的本地业务事务提交。跨仓部分失败时按同一订单键补查并恢复。若需新表，由选定 Owner 在自己的 Flyway 链新增迁移，声明表及字段注释、唯一键和必要索引，手写 SQL 走 Mapper XML。存量订单保持既有路径，本批只接范围生效后建立并可核验来源的试点订单。

**D3 营销侧双重校验活动与机器范围。** 运营沿用单门店满减工作台。保存、提审和发布的实际校验入口在实施时对照范围版本复核。Auth 签发的机器身份仅获得参与店的交易绑定权限。资金服务按版本核对现有签名订单声明，或新试点报价声明及交易持久证据。使用受信服务器上下文构造订单归属，来访参数仅作查找输入。若缺少签名或发布前的范围校验，沿用现有服务边界补齐该处。

## 4. 技术取舍与变更恢复

- 现有目录读接口与受控配置适合单店试点，运行成本集中在范围版本核对。范围名单在提审、放行和变更时校验，逐单门店归属在可信下单链路核验。现有 Java、MySQL、Mapper XML、OIDC/Casdoor 和发布流程覆盖首期需要。
- 批量跨租户门店同步、通用店铺主数据中心和自助管理页面属于后续多店场景。是否投入由首店验收后实际变更频率、跨门店授权和扩店需求决定。
- 目录读取失败保留失败原因并允许只读重查，缺证据的记录保持待核查。发现门店冻结、商品下架或归属调整时，先暂停试点活动的新参与，再核对存量申请和待处理回执。遇身份安全事件立即撤销对应机器授权，仍需补核的历史申请转由获授权的处置流程处理。历史已承诺订单按原报价、绑定和账本核对。新范围走新版复核后恢复，各系统分别提交本域变更及回执。
- 发布前验证实际 IAM 模式仍按租户及门店过滤。现有观测记录环境、范围版本、可脱敏的订单引用、失败类别和追踪号。运行告警接收方及生产阈值随目标环境签收。

## 5. 待评审和签收

| 项目 | 当前结论 | 对实施的影响 |
| --- | --- | --- |
| A1 目标环境与真实对象 | 目标环境、商户、门店、SKU 和出资账户待运营确认 | 可核对现有读取能力、准备脱敏表和隔离联调。真实范围签收取决于实际授权 |
| A2 逐单来源 | 本次已核对两边订单边界，已部署的受信下单关联待盘点 | 决定复用现有关系，或追加条件改造及验证 |
| R1 组织或门店编号串用 | 各系统的编号命名空间不同 | 优先验证显式映射及错租户、同名、对照店样本 |
| R2 范围状态变化 | 商品或门店在核验后可能发生变化 | 提审、发布和恢复时刷新证据，停用后保留历史义务 |
| R3 环境和验收混淆 | 既有本机及隔离记录能验证技术路径 | 试点范围、机器权限与真实同单凭证各自保留环境及签收记录 |

LC-02 的最终完成条件见[试点签收单](../../../../marketing-lowcode-platform/docs/delivery/lowcode-commercialization/READINESS.md#lc-02-试点签收单)。门店范围验收后可进入该清单的范围项，真实支付、两次部分退款、出资分摊及关账约定由交易和财务继续签收。
