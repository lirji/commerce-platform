# 技术选型与未知项闭合

|问题|决定与理由|验证|
|---|---|---|
|运营不断更换玩法|扩展已有受限类型 AST 与活动策略，配置版本不可变，发布与模拟分开；不用任意脚本|事实缺失、复杂度限制、旧活动兼容测试|
|是否引入 Drools|本轮不引入：现有比较/组合与有限价格策略可覆盖已批准范围；避免两套发布和事实语义|遇到无法表达的具体用例再开 ADR，而非预建通用引擎|
|定时人群/旅程|Spring 调度负责唤醒，MySQL 负责持久任务/检查点与效果幂等；复用现有事件组件|重启、重试、重复事件测试|
|成长正确性|会员域拥有账本，完成订单与退款事实驱动；按来源净额重新计算并做差额入账，避免重复/乱序直接加减|退款先到/多次/重复、并发测试|
|商品迭代|SKU 售价与状态保持旧投影，增加 SPU/规格与不可变修订；订单保留原报价快照|上下架、调价不重写历史订单|
|权限|新增 OPERATOR，ADMIN 平台全权；商家/店铺资源授权仅允许白名单经营动作。旧 admin 接口仍只 ADMIN|跨租户/越店/撤销后拒绝；不得将 OPERATOR 冒充 ADMIN|
|分析|领域 API 输出最小必要事实，分析模块拥有可重建投影；不跨域写权威表|合计与真实付款/退款事实核对|

没有新增中间件，也不升级依赖。吞吐/容量目标尚无业务输入，本轮仅证明有界处理与正确性，不承诺生产 QPS、HA 或 RTO。

官方依据（2026-09-23查阅）：[MySQL锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)说明 SKIP LOCKED 适合队列类处理，不用于普通一致性读取；[Spring调度](https://docs.spring.io/spring-framework/reference/integration/scheduling.html)提供唤醒能力，本项目恢复保障由数据库状态提供。
