# Phase 6 实现审查

## 审查范围与结论

审查 V41 迁移、活动发布校验、订单营销执行、内部 CREDIT 完成事件、运行时失败读取、管理查询、权限映射及集成测试。`marketing_execution` 的主键/约束与订单、支付、事件事务边界相符；读接口和 Mapper 写入均携带租户；规则器仍在纯 Java 模块中，未获写订单或权益能力。当前未发现阻止单 CREDIT 纵向切片交付的正确性问题。

## 具体检查

| 风险 | 检查与证据 | 结论 |
| --- | --- | --- |
| 重复订单、额度超发 | 订单命令幂等，执行主键，权益订单唯一键与额度条件更新；并发最后一份测试 | 通过 |
| 发放与投影崩溃窗口 | 权益状态、账本、可用事件同事务；营销更新依赖 Inbox 和条件状态；双实例测试 | 通过 |
| 历史版本漂移 | 执行保存活动/规则/人群/权益版本和报价 ID；v1/v2/回退测试 | 通过 |
| 越租户检查 | 所有执行 Mapper/事件查询带 `tenant_id`，跨租户管理员读为 404、会员为 403 | 通过 |
| 不安全历史重放 | 营销投影声明 `notReplayable`；原 `ReplayTest` 门禁通过；故障仅走原恢复 | 通过 |
| 发布无效配置 | 审批状态、时间、规则/人群/权益固定引用在发布事务复核；过期人群和重复分支负例 | 通过 |
| 假成功 | 参与先 `RESERVED`，支付后 `GRANT_REQUESTED`，只有真实 grant 可用才展示/投影 `GRANTED`；隔离显示 `GRANT_FAILED` | 通过 |

## 有界限制

1. `MARKETING_*` 能力在当前角色表中都授予租户 `ADMIN`；用例能力已分名，细分运营员角色及授权策略需要产品/安全决策。
2. 营销执行列表只返回持久状态，`GRANT_FAILED` 在详情合并运行时权威后显示；这样避免列表 N+1，但批量故障运营需用运行时隔离指标和恢复列表。
3. 本地 MySQL 样本单租户活动稀少，只证明索引与边界，不认证真实大租户 p95、吞吐或列表排序成本。
4. 单个内部 CREDIT 的退款后可见 `grantStatus=REVOKED/COMPENSATED`，执行 `GRANTED` 仍表示历史授予发生；补偿/当前可用余额以权益权威为准。礼包、外部提供者和新叠加策略未获产品语义。

审查未修改既有 Phase 2–5 运行时策略或跨域数据所有权。最终测试与浏览器分类见 `docs/evidence/phase6-marketing-platform/14-regression.md`。
