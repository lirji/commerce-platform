## 可行性与现状

- **结论：conditional-go。** 当前是 Java 21、Spring Boot 4.1.1、MyBatis、Flyway、MySQL 的模块化单体。受限规则树、纯 Java 决策、活动/规则/人群不可变版本、活动审批、权益配额与 Outbox/Inbox 已存在，可在现有架构上扩展。
- 活动 `marketing_campaign` 已按 `(tenant_id,campaign_id,version)` 保存内容；受治理活动引用 `marketing_rule_asset` 与 `marketing_audience_snapshot` 的固定版本。`CampaignService` 已有创建、审批、预览、发布、暂停与并发 `lock_version`，报价仅选择一个优惠最优活动。
- `QuoteService` 冻结活动选择、规则 Trace、人群来源和权益引用；`OrderService` 消费报价时预占预算及内部 CREDIT 权益，支付后由现有事件链请求发放。Phase 5 证明相应数据库幂等、额度条件更新和重投递保护。缺口是没有营销执行权威记录、触发到权益结果的统一追溯、发布完整校验与可检查的失败结果。
- 不接入 Drools、Kafka、Redis 或新服务。现有 `RuleNode`/`Condition` 的受限 AST 已支持本次所需规则。旧参考仓规则迁移仍是独立门禁，本次不改其历史解释。

## 产品行为与范围

- **代表活动：** 已存在的订单优惠活动，带固定版本人群快照、金额或会员规则、单个内部 CREDIT 权益。报价决策选中后，下单为参与触发，支付确认才请求发放。零元订单沿现有 `order.ready` 语义处理。
- **参与身份：** `(tenant_id, order_id, campaign_id)`；当前报价只选择一个活动，同一订单同一活动只能执行一次。下单前预览和报价均不发权益。配额在订单本地事务中预留，支付确认后转受理，异步消费者使其可用。
- **业务状态：** `RESERVED`、`GRANT_REQUESTED`、`GRANTED`、`RELEASED`、`GRANT_FAILED`（实际状态名在实施前与现有事件状态对齐）。规则未中选的原因留在报价 Trace，不伪造一条已经参与的执行记录。额度耗尽导致订单创建冲突，不能记录为成功发放。
- **版本与回退：** 执行记录保存活动、人群、规则、权益的精确版本及有界决策摘要；发布较新版本或恢复旧版本仅影响之后的报价/下单，既有发放不自动冲正。旧版本内容与报价快照始终可查询。
- **活动冲突：** 保留现有“最高优惠择优，活动 ID 稳定打破平局”的单选语义；非叠加券沿现有报价策略处理。本次不引入跨活动赠送或权益礼包原子性承诺。
- **权限：** 保留当前租户 `ADMIN` 管理入口，并为查看、编辑、审批/发布、暂停、预览和执行查看设置分别命名的用例权限检查；当前角色映射保持兼容，后续细分操作员授权属于独立产品决策。所有读写继续按可信 Actor 租户过滤。
- **非目标：** 新前端、全 CDP、通用脚本语言、现金/红包/返现、礼品、兑换码、多权益礼包、新消息系统、外部渠道回放、生产部署。

## 后端方案

1. **复用领域内核。** `marketing` 的 `Condition`/`RuleEvaluator`/`MarketingDecisionService` 保持纯计算；可信事实由 `CampaignService`/报价适配器准备。规则类型限定为当前比较、AND/OR/NOT、金额门槛、固定/百分比/阶梯和 SKU 范围。将决定原因和固定版本组合成有界执行摘要，不让规则调用持久化或权益。
2. **发布完整性。** 在 `CampaignService` 的现有审批/发布事务中校验活动、规则、人群、所引用权益、时间窗口和额度配置；未知节点由 `RuleNode` 现有拒绝路径处理。无权益引用的纯优惠活动继续合法，保留旧无 policy 活动的兼容发布语义，不回写旧 Flyway 迁移。
3. **订单执行。** 新 `CampaignExecutionApi`/服务放在 `marketing-runtime`，以订单选择快照为输入。在 `OrderService.create` 的同一事务记录参与，复用现有 `CampaignFundingApi.reserve` 和 `EntitlementApi.reserveOrder`；现有订单服务继续负责订单、库存和支付状态。执行表使用租户+订单+活动唯一约束，版本字段与状态条件更新，避免 JVM 锁。
4. **履约回填。** 复用现有 `order.paid.v1`、`order.cancelled.v1`、`benefit.grant.requested.v1` 事件与 Outbox/Inbox。若需要新增“发放已可用”事实，只由权益模块在持久化状态变化的同一事务追加有版本事件；营销消费者投影执行结果并使用其自己的 Inbox。失败先由现有事件运行时分类、重试、隔离和恢复，执行状态及检查接口展示未决/失败，不建立第二套重试器。
5. **持久化。** 追加一个 `V41` 之后的 Flyway 迁移（实施时以当前最大版本核对），新表及每列写中文注释，包含 `(tenant_id,order_id,campaign_id)` 唯一键、版本引用、状态、原因、金额/权益摘要和时间；不复制完整个人事实或敏感请求。现有 `benefit_definition`/`benefit_grant` 是额度与权益权威，不在营销表另设余额。
6. **接口与审计。** 延续 `/v1/admin/campaigns` 既有 API；增加按租户过滤的执行查询 API。使用现有命令/审核审计记录发布、回退、暂停，业务原因码与系统异常分开；指标仅以结果类型等低基数维度聚合。

## 运行、回退与风险

- 发布采取向前兼容迁移、先部署代码再启用新活动执行；功能观察以执行状态、事件积压、grant 失败和额度异常为准。回退活动配置只切换未来候选版本；代码回退需保持新表可读并保留历史记录，不回滚已发权益。
- 当前权益提供者只证明内部 CREDIT，外部渠道不宣称通过。额度失败时订单事务回滚，已付款后的异步发放失败必须留在运行时恢复队列，不进行不安全的二次授予。
- 粗略工作规模：跨 4 个服务端模块、1 个迁移和集成证据的多阶段交付。最大不确定性是发放结果事件与旧订单创建时序的兼容；在第一个真实 MySQL 触发切片后复核范围。
- 待定产品项：多权益礼包原子性、跨活动叠加与专属优先级、外部财务类权益、细分操作员授权。当前单活动单 CREDIT 路径有既有语义，可以独立推进。
